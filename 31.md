# NUT-31: Nut Fungible Tokens

`draft`

`depends on: NUT-00, NUT-01, NUT-03, NUT-04, NUT-06, NUT-10`

`uses: NUT-07, NUT-11, NUT-12, NUT-28`

* * *

## Abstract

This document specifies Nut Fungible Tokens (NutFT), an application extension
for Cashu proofs that represent individually identifiable bearer assets.

NutFT reuses Cashu's blind signatures, keysets, proofs, spending conditions,
swaps, and optional DLEQ proofs. It adds a canonical application asset payload
and rules that prevent a mint or wallet operation from replacing an asset proof
with a proof that has lost or changed its asset metadata.

NutFT does not define a blockchain, a marketplace, a game engine, or a
universal metadata catalog. Asset metadata is visible to the mint, which may
know the asset identifier, asset metadata, and trading volume. Applications
MAY use P2BK (NUT-28) to reduce linkability of recipient public keys.

This document is a draft application proposal. It is not an official Cashu
NUT assignment.

## Motivation

Cashu proofs are bearer assets identified by a secret and a mint signature.
Cashu's standard amount and unit fields are sufficient for ordinary fungible
value, but applications may need one indivisible proof to represent one
collectible, entitlement, credential, or other identifiable asset.

Without application rules, an ordinary Cashu swap can produce a valid Cashu
result while dropping the application payload. NutFT makes the asset payload
part of the mint-validated secret and requires replacement proofs to preserve
the same asset binding.

## Relationship to NUT-22

NUT-22 demonstrates that Cashu proofs can serve as application-layer bearer
credentials rather than ordinary payment value. Its blind authentication
tokens (BATs) use `unit=auth` and `amount=1`, and are consumed once to
authorize access to a protected endpoint.

NutFT applies the same Cashu primitives to persistent, individually
identifiable application assets. Unlike a BAT, a NutFT replacement proof MUST
preserve the same asset binding while ownership and spending-condition data
change. NUT-22 is the protocol precedent; it does not define NutFT metadata
or asset replacement rules. See [NUT-22: Blind authentication](https://github.com/cashubtc/nuts/blob/main/22.md).

## Terminology

- **Asset:** an individually identifiable application object represented by a
  NutFT proof.
- **Asset catalog:** application-controlled data describing assets.
- **Asset reference:** the canonical fields that identify an asset and locate
  its catalog.
- **Asset binding:** a digest of the canonical asset reference.
- **NutFT proof:** a Cashu proof whose secret is a valid `NutFTSecret`.
- **Replacement proof:** a proof created by swap, trade, or another operation
  that consumes an earlier NutFT proof.

## Capability advertisement

A mint supporting NutFT MUST advertise the capability in the `nuts` object of
its NUT-06 info response. The following is the NutFT capability value:

```json
{
  "nuts": {
    "31": {
      "supported": true,
      "versions": [1],
      "output_openings": true,
      "p2bk": true,
      "dleq": true
    }
  }
}
```

The capability fields are:

- `supported`: whether the mint accepts NutFT proofs;
- `versions`: supported NutFT secret versions;
- `output_openings`: whether the mint validates disclosed output secrets and
  blinding factors;
- `p2bk`: whether NutFT transfers accept NUT-28 destinations;
- `dleq`: whether NutFT outputs include NUT-12 DLEQ proofs.

Wallets MUST NOT send NutFT operations to a mint that does not advertise the
required capability.

## Unit and amount

The Cashu `unit` MUST equal the stable `collection_id` of the asset catalog.
This keeps each collection in its own Cashu namespace; a game may use one or
more collections, but NutFT does not require a game.

Every individual NutFT proof MUST have `amount=1`. Wallets MAY aggregate
identical assets in their user interface, but MUST keep the underlying proofs
separate and MUST NOT create a proof with an amount greater than `1` for a
single NutFT asset binding.

The mint MUST validate that the proof's keyset and unit are valid for the
application namespace.

## Asset reference and binding

The asset reference is a canonical object. NutFT version 1 defines the
following required fields:

```json
{
  "collection_id": "<stable-collection-identifier>",
  "asset_id": "<application-defined-identifier>",
  "catalog_uri": "<canonical-catalog-location>"
}
```

The reference contains only the identity of the asset and the location of its
catalog. Applications MUST NOT add other application data to the token.
Metadata such as artwork, attributes, rarity, rules, and descriptions belongs
in the catalog. The catalog schema and its authority are application-defined
and are not specified by NutFT.

`catalog_uri` MUST be a canonical URI. It locates the catalog; it does not by
itself authenticate catalog contents. Applications and mints MAY apply their
own catalog validation rules.

The asset binding is:

```text
asset_binding = SHA256(
  UTF8("Cashu_NutFT_v1") ||
  canonical_json(asset_reference)
)
```

`canonical_json` MUST use UTF-8, lexicographically sorted object keys, no
insignificant whitespace, and the JSON representation defined by the
application. Implementations MUST reject ambiguous encodings.

The following values MUST NOT be included in `asset_binding`:

- owner public keys;
- P2BK ephemeral public keys;
- Cashu secret nonces;
- blind factors;
- DLEQ proof values;
- proof-specific nullifiers.

Those values can change when ownership changes while the represented asset
remains the same.

## NutFT secret

NutFT version 1 extends the NUT-10 well-known `Secret` with a `nutft` tag.
The spending-condition kind remains the outer `Secret` kind. An
implementation MAY use `P2PK`, which NUT-28 can extend to P2BK:

```json
[
  "P2PK",
  {
    "nonce": "<unique-random-string>",
    "data": "<compressed-public-key>",
    "tags": [
      [
        "nutft",
        "1",
        "collection-alpha",
        "set-alpha:001",
        "https://catalog.example/collection-alpha/set-alpha:001",
        "<asset-binding>"
      ],
      ["sigflag", "SIG_INPUTS"]
    ]
  }
]
```

The `nutft` tag MUST occur exactly once and MUST contain, in order:

```text
["nutft", version, collection_id, asset_id, catalog_uri,
 asset_binding]
```

All tag values MUST be non-empty strings. The tag is part of the serialized
secret and therefore part of the Cashu-signed message. The `asset_binding`
MUST equal the binding computed from the preceding reference fields. The
remaining tags and `data` field MUST follow the spending semantics of the
selected NUT-10 spending condition.

When NUT-28 is used, the proof MUST carry the NUT-28 ephemeral-key field and
the `data` public key in the P2PK secret MUST be the corresponding blinded key.

The `nutft` tag is understood only by a NutFT-aware mint. A generic P2PK mint
may be able to parse the surrounding secret but MUST NOT be assumed to
preserve NutFT semantics. This document does not change the Cashu blind
Diffie-Hellman key exchange and does not define a new signature algorithm.

## NutFT output openings

NutFT version 1 prioritizes exact asset preservation over output-to-proof
unlinkability. NutFT-aware minting and transfer requests MUST carry the
following opening alongside each blinded output:

```json
{
  "amount": 1,
  "id": "<keyset-id>",
  "B_": "<blinded-message>",
  "nutft": {
    "secret": "<canonical-serialized-NutFT-secret>",
    "blinding_factor": "<32-byte-hex-scalar>",
    "p2pk_e": "<optional-NUT-28-ephemeral-key>"
  }
}
```

The mint MUST parse and validate `nutft.secret`, recompute the blinded message
from that secret and `nutft.blinding_factor`, and require it to equal `B_`
before signing. It MUST reject an invalid scalar, a non-canonical secret, a
malformed NutFT tag, or a mismatched blinded message. The mint derives the
asset reference and binding from the validated secret; no separate asset
declaration is needed. `blinding_factor` MUST encode a valid non-zero secp256k1
scalar as 32-byte lowercase hexadecimal. When NUT-28 is used, `p2pk_e` MUST
equal the ephemeral-key field that will be carried by the resulting proof.

Revealing the secret and blind factor lets the mint link the issued output to
the resulting proof. This is an explicit NutFT version 1 tradeoff: asset
identity is not blinded and exact binding preservation is required without a
zero-knowledge proof. P2BK still keeps the recipient's long-lived public key
out of the disclosed secret.

## Issuance

Issuance MUST follow the Cashu minting flow defined by NUT-04. Before signing a
NutFT output, the mint MUST additionally:

1. validate the disclosed output secret and blind factor against `B_`;
2. validate the supported NutFT version;
3. validate `amount=1` and require `unit=collection_id`;
4. compute the expected asset binding from the disclosed secret;
5. apply any application-defined catalog policy.

The mint MAY know the asset identifier and asset metadata. NutFT version 1
does not require the mint to hide asset identity from itself.

If NUT-12 is supported, the mint MUST include a DLEQ proof for the output.
Wallets MUST verify the DLEQ proof before accepting the output.

DLEQ proves that the mint used the same signing key for the blinded message and
the advertised keyset. DLEQ does not prove catalog membership, metadata
validity, ownership, or unspent state.

## Validation

A wallet or verifier MUST validate, as applicable:

1. Cashu proof structure, amount, unit, keyset, and mint;
2. the canonical NUT-10 secret and its `nutft` tag;
3. `asset_binding` against the asset reference;
4. the catalog located by `catalog_uri`, according to application-defined
   catalog rules;
5. the P2PK/P2BK spending condition, when used;
6. the DLEQ proof, when present;
7. the current proof state when an online state check is required.

An application catalog is external to the token. A wallet MUST NOT treat
display metadata as authoritative unless it follows the catalog rules chosen
by the application. NutFT itself does not define a catalog authority,
catalog signature, or metadata schema.

## Swap and replacement proofs

NutFT replacement uses the Cashu swap operation from NUT-03 or an equivalent
NutFT-aware atomic operation. For every consumed input and replacement output,
the mint MUST validate both secrets, compute their bindings, and enforce:

```text
output.asset_binding == input.asset_binding
```

The replacement proof MAY have a different:

- owner public key;
- P2BK ephemeral key;
- secret nonce;
- blind factor;
- DLEQ proof;
- Cashu proof commitment.

The replacement proof MUST still have `amount=1`, the same application unit,
and the same canonical asset reference and binding.

The mint MUST validate all inputs before marking any input spent. If the
operation fails, the original proofs MUST remain spendable. If the response is
lost after a successful commit, the operation MUST be recoverable using the
mint's normal idempotency or state-recovery mechanism.

An application-level trade is therefore:

```text
consume(old_proof, valid_owner_witness)
issue(new_proof, new_owner_destination)
```

When the new destination uses P2BK, the mint MAY see the blinded recipient key
but MUST NOT require the recipient's long-lived public key to be present in the
asset binding.

## P2PK and P2BK

NutFT transfers MAY use ordinary P2PK spending conditions as defined by NUT-11.
They MAY use NUT-28 P2BK when supported.

P2BK protects the recipient key and reduces key-based linkability. It does not
hide the asset reference or asset metadata from the mint. NutFT version 1 does
not define card-blinded or metadata-blinded transfers.

Mints and wallets MUST check the `p2bk` capability before using P2BK.

## Generic Cashu compatibility

A Cashu implementation that does not support NutFT MAY transport an opaque
token, but MUST NOT claim to validate or preserve its application semantics.

A mint MUST reject a generic swap or other operation that consumes a NutFT
proof and issues a new proof without a valid NUT-10 secret, a valid `nutft`
tag, and the same `asset_binding`.

Wallets SHOULD display an explicit unsupported-token error instead of silently
converting a NutFT proof to ordinary Cashu value.

## Error conditions

The following application errors are recommended:

- `nutft_unsupported`: the mint or wallet does not support the requested
  NutFT version;
- `nutft_invalid_secret`: the secret is malformed or non-canonical;
- `nutft_invalid_reference`: the asset reference is invalid;
- `nutft_binding_mismatch`: the computed binding differs from the secret;
- `nutft_catalog_rejected`: the catalog entry is not accepted by an
  application-defined catalog policy;
- `nutft_binding_not_preserved`: a replacement output changes the asset.

Mints MUST reject malformed or non-canonical secrets before consuming proofs.

## Security considerations

### Metadata integrity

Catalog locations are transport references. Applications define how catalog
contents are authenticated and validated; a server hosting a catalog is not
automatically an authority merely because it serves the content.

### Binding preservation

The asset binding MUST be covered by the Cashu-signed secret. A display-only
field, memo, or unsigned token extension is insufficient.

### Double spending

P2PK/P2BK signatures prove control of a spending condition; they do not prevent
double spending. The mint's spent and pending state, together with atomic
operation handling, remains authoritative.

### Privacy

NutFT version 1 does not hide asset identity from the mint. P2BK reduces
recipient-key linkability but does not prevent correlation through account
records, payment metadata, network logs, or application-level identifiers.

### Downgrade and stripping

Implementations MUST NOT silently downgrade a NutFT proof to ordinary Cashu or
strip its secret during a swap. Capability negotiation and explicit rejection
are safer than lossy compatibility.

### Untrusted application data

Catalog entries and properties MUST be treated as data. Clients MUST NOT
execute arbitrary code supplied by a token or metadata server.

## Test vectors and interoperability

A complete implementation SHOULD publish vectors covering:

- canonical asset references and bindings;
- valid and invalid `NutFTSecret` values;
- valid DLEQ proofs;
- P2PK and P2BK destinations;
- successful replacement with an unchanged binding;
- rejection of a changed collection identifier, asset identifier, or catalog
  location;
- rejection of generic metadata-dropping replacements;
- failed operations that leave the old proof unspent;
- idempotent recovery after a lost response.
